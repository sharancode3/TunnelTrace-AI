# RFC 4303
## IP Encapsulating Security Payload (ESP)

**Authority:** Internet Engineering Task Force (IETF)  
**Publication Date:** December 2005  
**Status:** APPROVED / ACTIVE / PROPOSED STANDARD  
**Document Code:** RFC 4303  
**URL:** https://datatracker.ietf.org/doc/html/rfc4303  

---

### Section 2.1 ESP Packet Format and Structure
The Encapsulating Security Payload (ESP) provides confidentiality, data origin authentication, connectionless integrity, and anti-replay service:
- The ESP header consists of a 4-byte Security Parameters Index (SPI) and a 4-byte Sequence Number field.
- The Payload Data contains the encrypted transport-layer or inner IP packet, followed by ESP Padding, Pad Length (1 byte), and Next Header (1 byte).
- Following the encrypted payload is the Integrity Check Value (ICV), which authenticates the ESP header and ciphertext payload.

### Section 3.3.3 Sequence Number Generation and Anti-Replay Protection
The Sequence Number field is a mandatory 32-bit (or 64-bit Extended Sequence Number) counter:
- The sender MUST increment the Sequence Number by exactly one for every transmitted ESP packet. Sequence numbers MUST be strictly monotonic and MUST NOT cycle without rekeying the Security Association.
- If sequence number counter reaches maximum ($2^{32}-1$) and Extended Sequence Numbers (ESN) are not negotiated, transmission on this SA MUST cease and an SA rekey MUST occur.

### Section 3.4.3 Anti-Replay Window Verification
The receiver uses a sliding window mechanism to defend against replay attacks:
- The receiver maintains an anti-replay window (typically 64 or 128 packets minimum size).
- Any incoming packet with a sequence number strictly lower than the lower edge of the window MUST be rejected and logged as an anti-replay failure.
- Packets within the window that have already been received MUST be rejected to prevent replay injection.
