# RFC 7296
## Internet Key Exchange Protocol Version 2 (IKEv2)

**Authority:** Internet Engineering Task Force (IETF)  
**Publication Date:** October 2014  
**Status:** APPROVED / ACTIVE / PROPOSED STANDARD  
**Document Code:** RFC 7296  
**URL:** https://datatracker.ietf.org/doc/html/rfc7296  

---

### Section 1.2 The Initial IKE Exchanges
IKEv2 establishes security associations using a fixed sequence of request/response exchanges:
- An initial IKE exchange begins with the `IKE_SA_INIT` exchange, in which peers negotiate cryptographic algorithms, exchange nonces, and perform a Diffie-Hellman exchange.
- Following `IKE_SA_INIT`, the peers execute the `IKE_AUTH` exchange, which authenticates the peers' identities, verifies certificates or pre-shared keys, and establishes the first Child SA (ESP or AH).
- IKEv2 replaces the multi-phase complexity of legacy IKEv1 (Main Mode, Aggressive Mode, Quick Mode) with a consolidated, streamlined, and cryptographically resilient architecture.
- Deprecated legacy IKEv1 protocols SHALL NOT be used for new IPsec deployments due to offline PSK dictionary vulnerabilities in Aggressive Mode and known protocol state machine race conditions.

### Section 1.3 Creating and Rekeying Child SAs
Subsequent Child SAs or rekeys of existing Child SAs are negotiated using the `CREATE_CHILD_SA` exchange:
- To achieve Perfect Forward Secrecy (PFS), the initiator of a `CREATE_CHILD_SA` request SHALL include a Key Exchange (KE) payload containing fresh ephemeral Diffie-Hellman public data.
- The responder SHALL evaluate the proposed KE transform and include its own KE payload in the response.
- If the KE payload is omitted from the `CREATE_CHILD_SA` exchange, the new Child SA keys are derived strictly from the existing IKE SA keying material without Diffie-Hellman re-negotiation (PFS disabled).

### Section 3.3 Security Association Payload (SA)
The Security Association (SA) payload contains one or more Proposals:
- Each Proposal contains a proposal number, a protocol ID (IKE, ESP, AH), an SPI size, and a list of Transform Substructures.
- Transform types include Transform Type 1 (Encryption / ENCR), Transform Type 2 (Pseudo-random function / PRF), Transform Type 3 (Integrity / INTEG), Transform Type 4 (Diffie-Hellman Group / D-H), and Transform Type 5 (Extended Sequence Numbers / ESN).
- A responder MUST accept exactly one Proposal from the initiator's list, selecting exactly one transform of each mandatory transform type.
